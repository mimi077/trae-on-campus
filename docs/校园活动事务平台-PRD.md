## 1. 项目目标

**一句话目标**：把分散在群公告、海报和公众号里的校园活动，收拢到一个「可审核、可报名、可统计」的事务平台——学生用学号登录即可发现活动、完成报名、管理自己的参与记录；教师与活动事务处用同一套后台完成发布、审核、名额与名单管理。

**产品契约**：

| 项 | 定义 |
| --- | --- |
| 主要用户 | 在校学生（浏览与报名）；教师 / 活动事务处老师（发布与审核） |
| 触发场景 | 学生想找一场能参加的活动；老师要发布官方活动或审批社团活动 |
| 核心任务 | 发布 → 审核 → 展示 → 报名 → 参与 → 结果可追踪 |
| 完成条件 | 学生报名成功并在「我的活动」看到记录；老师在审核队列与报名名单中看到完整数据 |
| 信任基础 | 学号 / 工号实名、官方认证标识、服务端审核与审计日志 |

**MVP 判定标准**：评审时能连续演示一条完整主流程，不依赖真实教务系统（可用演示账号与 Mock 身份），不要求高并发与长期运行。

**成功标志（可验收）**：

1. 教师用管理员账号发布一场「官方活动」，学生端列表立即出现并带官方认证标识。
2. 学生用学号登录，按「官方 / 校级 / 院系 / 社团」与关键词筛选到活动，打开详情看到时间、地点、名额与报名链接。
3. 学生报名成功，名额数字实时变化，「我的活动」出现「已报名」，重复报名被拦截。
4. 社团提交的活动进入 `PENDING`，公开列表不可见；教师在审核队列通过后立即公开，驳回可填写原因。
5. 报名截止后、活动取消后、名额已满时，报名入口均被正确拦截并给出明确原因。

## 5. 业务规则、边界约束与并发风险（核心章节）

> 原则：前端校验只做体验优化，**关键规则必须在后端再校验一次**；各功能单测通过 ≠ 全局并发安全。

### 5.1 操作时序约束

| 规则 | 说明 | 校验位置 |
| --- | --- | --- |
| 发布前置 | 标题、类型、时间、地点、名额、报名方式必填；`startAt < endAt`；`registrationDeadline <= startAt` | 前端表单 + 后端 Zod |
| 报名前置 | 活动必须是 `PUBLISHED`；当前时间早于报名截止；活动尚未开始；名额未满 | 后端 mutation |
| 审核前置 | 只有 `PENDING` 活动可审核；只有教师 / 管理员可操作；驳回必须填写原因 | 后端 `adminProcedure` |
| 取消报名前置 | 报名状态为 `PENDING` / `APPROVED`；距活动开始超过 2 小时（可配置）；已签到不可取消 | 后端 mutation |
| 外链跳转 | 先弹出「即将跳转外部链接」确认，再 `new tab` 打开 | 前端 + 链接白名单校验 |
| 状态不可逆 | `ENDED`、`CANCELLED`、`REJECTED` 为终态，不能被改回已发布 | 后端状态机校验 |

### 5.2 共享资源互斥（并发核心）

| 资源 | 互斥条件 | 冲突后果 | 处理方式 |
| --- | --- | --- | --- |
| 活动名额 | `已占用名额 < capacity` 才允许创建报名 | 超卖、报名人数超过上限 | 事务内「查已占用 → 判断 → 写入」；已满返回 `CAPACITY_FULL` |
| 同一用户同一活动 | `userId + activityId` 只允许一条有效报名 | 重复报名、名额被同一人占用多次 | 数据库联合唯一索引 + 后端幂等返回已有记录 |
| 审核动作 | 同一活动只允许一次 `PENDING → APPROVED/REJECTED` | 重复审核、状态来回跳 | 更新时带 `status = "PENDING"` 条件；已审核返回幂等结果 |
| 取消报名与名额回补 | 取消成功后占用名额减 1 | 名额不释放导致后续无法报名 | 取消与计数在同一事务内完成 |
| 活动取消 | 仅 `PUBLISHED` / `ONGOING` 可取消 | 已结束活动被误取消 | 状态机校验 + 二次确认弹窗 |

> 实现要求：MVP 不引入分布式锁，但必须做**提交前二次状态校验**；SQLite 下的写事务使用 `db.$transaction` 串行化关键写入。

**名额计算口径（全文唯一）**：

```
已占用名额 = 状态为 PENDING 或 APPROVED 的报名数量
剩余名额   = max(capacity - 已占用名额, 0)
是否已满   = 剩余名额 == 0
```

### 5.3 次数与身份边界

| 规则 | 说明 |
| --- | --- |
| 单活动单用户 | 同一学号对同一活动只能有一条有效报名；取消后可重新报名，但会生成新记录 |
| 并发报名上限 | 同一学生最多同时持有 20 个未结束活动的有效报名 `[假设]` |
| 发布者限制 | 教师不能报名自己发布的活动；教师可报名其他教师发布的活动 |
| 身份识别 | 学生用学号、教师用工号；同一登录页根据账号类型自动路由，登录后角色以数据库为准 |
| 重复提交 | 10 秒内相同用户 + 相同活动 + 相同操作视为重复请求，返回已有结果（幂等） |
| 前端限制 | 提交中按钮置灰、Loading，仅作体验优化 |

### 5.4 输入与数据边界

| 规则 | 说明 |
| --- | --- |
| 必填校验 | 标题、类型、主办方、开始/结束时间、报名截止、地点、名额、报名方式 |
| 长度边界 | 标题 2–60 字；地点 2–60 字；简介 500 字；详情 5000 字；报名链接 500 字；留言 1–300 字 |
| 时间边界 | 结束时间必须晚于开始时间；报名截止不得晚于开始时间；新发布活动的开始时间不得早于当前时间 2 小时 `[假设]` |
| 名额边界 | 1–2000 的整数；外链活动名额可留空并显示「以主办方为准」 |
| 链接边界 | 仅允许 `http://` / `https://`；拒绝 `javascript:`、`data:`、相对路径 |
| 枚举边界 | 活动类型、来源标签、报名方式、状态均为固定枚举，非法值直接拒绝 |
| 数据规模 | MVP 支持 500 场活动、5000 条报名；列表默认 12 条/页 |
| 数据策略 | SQLite 文件持久化；线上演示环境落在 `/tmp`，实例重启即重置，属可接受限制 |

### 5.5 状态机与流转

**活动状态**

| 状态 | 含义 | 进入条件 | 可执行操作 |
| --- | --- | --- | --- |
| `DRAFT` | 草稿（P1） | 教师保存未发布 | 编辑、提交审核、删除 |
| `PENDING` | 待审核 | 社团 / 院系 / 学生组织提交 | 教师通过 / 驳回；发布者撤回 |
| `PUBLISHED` | 报名中 | 教师直接发布或审核通过 | 学生报名、教师取消、编辑非关键字段 |
| `ONGOING` | 进行中 | 到达开始时间自动流转 | 停止新报名、查看名单（P1 签到） |
| `ENDED` | 已结束 | 到达结束时间自动流转 | 仅查看、导出名单 |
| `CANCELLED` | 已取消 | 教师取消或主办方撤回 | 仅查看；已报名学生收到状态提示 |
| `REJECTED` | 已驳回 | 教师驳回并填写原因 | 发布者修改后重新提交 |

**报名状态**

| 状态 | 含义 | 进入条件 | 可执行操作 |
| --- | --- | --- | --- |
| `PENDING` | 待审核（需审核的活动） | 学生提交报名 | 教师通过 / 拒绝；学生取消 |
| `APPROVED` | 已报名 | 直接报名或教师通过 | 学生取消（开始前 2 小时外） |
| `REJECTED` | 报名被拒 | 教师拒绝 | 查看原因，不可再次报名同一场 |
| `CANCELLED` | 已取消 | 学生取消或活动取消 | 可重新报名（若仍开放） |
| `ATTENDED` | 已签到（P1） | 现场核销 | 仅查看 |

**自动流转规则**：不引入定时任务，采用与 V5 到期下架一致的**惰性计算**——在读取列表、详情、我的活动或报名时，根据当前时间计算展示状态并落库修正；保证任何页面读到的时间状态一致。

### 5.6 外链与内容安全

1. 报名链接只允许 `http(s)`，服务端与前端双重校验；`javascript:` 一律拒绝。
2. 外链报名活动显示「外部报名」标签，按钮先弹确认：「将跳转到主办方页面，报名结果以主办方为准」。
3. 平台不抓取、不代理外链内容，不保证链接长期有效；失效由主办方负责更新。
4. 活动标题与详情禁止出现与活动无关的广告引流；审核不通过时须写明原因。
5. 公开名单只显示「学院 + 姓名首字」，完整名单仅教师可见，避免隐私泄漏。
6. 留言公开可见，禁止填写手机号、身份证号；后端对明显手机号做提示性拦截（P1 自动脱敏）。

### 5.7 教务平台对接边界

| 项 | 产品约定 |
| --- | --- |
| 登录方式 | 学号 / 工号 + 密码 → 教务身份接口校验；校方支持 CAS / OAuth2 / 开放 API 时优先走 SSO |
| 首登同步 | 首次登录写入姓名、学院、专业、年级；后续以教务返回数据为准，学生只能修改头像色与简介 |
| 失败降级 | 教务接口超时（3 秒）或不可用时，降级为本地演示账号，并在登录页标注「演示模式」 |
| 异常身份 | 学号不存在、已毕业、休学、账号冻结 → 拒绝登录并给出可操作提示 |
| 并发首登 | 同一学号并发首次登录使用 upsert，保证只产生一条用户记录 |
| 凭据安全 | 平台不存储教务密码，只保存校方返回的唯一标识与必要资料 |
| 数据最小化 | MVP 只同步身份字段；课表、成绩、学分在获得显式授权前不读取 |
| 回写教务（P1） | 活动结束且教师确认后，批量回传学分 / 志愿时长，并记录「待回传 / 成功 / 失败」状态，失败可重试 |

### 5.8 UI 层级与遮挡约束

1. 所有下拉、弹窗、二级选择浮层使用 `createPortal` 挂载到 `body`，`z-index` 高于内容区（沿用 V5 的 Portal Select 方案）。
2. 浮层根据视口剩余空间自动向上/向下翻转，不被卡片、表格或滚动容器裁切。
3. 活动标题与筛选区下方的内容不得因浮层展开被压缩。
4. 弹窗居中浮层显示，不挤压页面原有布局；移动端改为全宽抽屉。
5. 长名单、长留言使用固定高度 + 内部滚动，避免撑破布局。

### 5.9 异常兜底

| 场景 | 前端表现 | 后端返回 |
| --- | --- | --- |
| 提交中 | Loading、按钮置灰、禁止重复点击 | — |
| 名额已满 | 按钮变为「名额已满」并禁用 | `CAPACITY_FULL` + 剩余名额 |
| 重复报名 | 提示「你已报名该活动」，跳转我的活动 | 幂等返回已有报名 |
| 报名截止 / 活动已开始 | 按钮禁用并说明原因 | `REGISTRATION_CLOSED` |
| 活动已取消 | 详情页顶部状态条 + 报名按钮禁用 | `ACTIVITY_CANCELLED` |
| 权限不足 | 隐藏入口或提示「仅教师可操作」 | `FORBIDDEN` |
| 请求失败 | 提示「请重试」，不白屏 | 统一错误结构 `{ ok, message }` |
| 空数据 | Empty State 占位 + 引导发布 / 清除筛选 | 空数组 |
| 教务登录失败 | 提示具体原因与「使用演示账号」入口 | `AUTH_UPSTREAM_FAILED` |

| 场景 | 是否覆盖 | 处理 |
| --- | --- | --- |

## 8. 后端设计要点

### 8.1 数据模型（Prisma 模型清单）

| 模型 | 关键字段 | 说明 |
| --- | --- | --- |
| `User` | id、name、studentNo、role、college、major、grade、passwordHash、avatarColor | 学生 / 教师共用，`role = STUDENT / TEACHER / ADMIN` |
| `Session` | token、userId、expiresAt | 沿用 V5 会话表 |
| `Activity` | id、title、type、source、organizer、startAt、endAt、registrationDeadline、location、capacity、registrationMode、externalUrl、description、coverUrl、tags、status、createdBy、reviewNote、reviewedBy | 活动主表 |
| `Registration` | id、activityId、userId、status、note、createdAt | `@@unique([userId, activityId])` |
| `ActivityMessage` | id、activityId、userId、content | 公开答疑留言 |
| `Favorite` | id、userId、activityId | 收藏关注（P1，可先建表不开放） |
| `Report` | id、reporterUserId、targetActivityId、reason、status | 举报（P1） |
| `AdminLog` | id、adminUserId、action、targetId | 发布 / 审核 / 取消留痕，沿用 V5 |

**固定枚举**：

- 活动类型 `type`：`LECTURE` 讲座、`COMPETITION` 比赛、`VOLUNTEER` 志愿服务、`CLUB` 社团活动、`CAREER` 就业宣讲、`SPORTS` 体育活动、`OTHER` 其他。
- 活动来源 `source`：`OFFICIAL` 官方活动、`SCHOOL` 校级活动、`COLLEGE` 院系活动、`CLUB` 社团活动。
- 属性标签 `tags`：`CREDIT` 可加学分、`HOURS` 志愿时长、`PRIZE` 有奖品、`AUDIT` 需报名审核、`MEAL` 提供餐饮。
- 报名方式 `registrationMode`：`INTERNAL` 站内报名、`EXTERNAL` 外链报名、`BOTH` 同时支持。
- 状态见 5.5。

### 8.2 状态机实现原则

1. 所有状态变更集中在 `activity` 与 `registration` 两个 router，禁止在页面组件里拼接状态。
2. 惰性流转函数 `syncActivityStatus()`：读取活动前调用，按当前时间把 `PUBLISHED → ONGOING → ENDED` 落库，沿用 V5 `expireStaleItems()` 模式。
3. 状态变更必须带「当前状态」条件更新，防止并发覆盖。
4. 每次审核、取消写入 `AdminLog`；学生取消报名写入 `Registration` 历史状态与时间。

### 8.3 接口清单（tRPC procedure）

| 接口 | 类型 | 入参 | 返回 | 校验点 |
| --- | --- | --- | --- | --- |
| `activity.list` | query | keyword、type、source、tag、timeRange、status、page | 分页列表 + 报名数 | 只返回公开状态 |
| `activity.byId` | query | id | 详情 + 名额 + 我的报名状态 | 非公开状态仅发布者/教师可见 |
| `activity.create` | mutation | 活动字段 | id + status | 时序、长度、枚举、链接、权限 |
| `activity.update` | mutation | id + 字段 | 更新结果 | 仅草稿/驳回可改关键字段 |
| `activity.cancel` | mutation | id | status | 仅教师；状态机校验 |
| `activity.review` | mutation | id、action、note | status | 仅 ADMIN；PENDING 才能审；驳回必填原因 |
| `activity.pendingCount` | query | — | 数量 | 仅 ADMIN |
| `registration.create` | mutation | activityId | 报名记录 | 名额互斥、重复、截止、状态、黑名单 |
| `registration.cancel` | mutation | activityId | 结果 | 归属、时间窗口、状态 |
| `registration.mine` | query | status、page | 我的报名列表 | 按当前用户 |
| `registration.roster` | query | activityId | 名单 + 学院分布 | 仅 ADMIN / 发布者 |
| `activityMessage.list` | query | activityId | 留言列表 | 活动可见性 |
| `activityMessage.create` | mutation | activityId、content | 留言 | 长度、状态、频率 |

### 8.4 实现约束

1. **类型先行**：先用 Zod 定义输入输出，tRPC 自动推导前端类型。
2. **校验在后端**：名额、状态、权限、时间窗口判断全部写在 mutation 内。
3. **写入前复核**：报名与审核在事务内重新读取状态再写入。
4. **统一返回结构**：错误使用 `TRPCError` + 明确 message，前端统一提示。
5. **审计留痕**：发布、审核、取消、名单导出都写 `AdminLog`。
6. **不实现页面不存在的接口**，避免范围膨胀。

### 8.5 并发自检清单（代码写完对照打勾）

- [ ] 报名提交前有「已占用名额」复核
- [ ] 重复报名不会产生两条记录（唯一索引兜底）
- [ ] 报名截止与活动开始以服务端时间判定
- [ ] 审核只能处理 `PENDING`，重复审核幂等
- [ ] 取消报名后名额正确回补
- [ ] 非公开活动不能被普通学生通过 URL 访问
- [ ] 权限校验在服务端，前端隐藏按钮不作为防线
- [ ] 空数据与错误都有兜底返回

## 11. 演示脚本（答辩用）

1. `npm run dev` 启动，展示活动广场：英雄区、来源标签、报名人数、筛选区。
2. 教师登录，发布一场「官方活动」，填写时间、名额、外链报名；列表立即出现官方认证标识。
3. 学生登录，按「官方活动 + 可加学分」筛选，打开详情，展示报名进度与留言。
4. 点击报名 → 名额 +1 → 「我的活动」出现已报名；再次点击被拦截。
5. 打开第二场仅剩 1 个名额的活动，连续报名两次，第二次提示「名额已满」。
6. 社团提交活动 → 教师审核队列驳回并填写原因 → 学生在我的活动看到驳回原因。
7. 教师重新通过另一场活动 → 公开列表出现 → 查看报名名单与学院分布。
8. 收尾：一句话技术栈、复用 V5 的框架能力、后续创新方向。

## 12. 风险预案

| 风险 | 触发信号 | 预案 |
| --- | --- | --- |
| 名额并发超卖 | 两人同时报名最后 1 个名额 | 事务内复核 + 唯一索引；现场用两个浏览器演示拦截 |
| 教务对接不可用 | 登录接口超时 | 立即切演示账号，登录页标注演示模式 |
| 时间判断不一致 | 客户端与服务端时间不同 | 全部以服务端时间判定，客户端只做提示 |
| Schema 变更冲突 | 现场要加字段 | 提前在 `bootstrap.ts` 补列，禁止现场改表 |
| 合并冲突 | 两人改同一文件 | 回退上一稳定版本，按文件所有权重新分配 |
| 时间不足 | 80min 主流程未通 | 砍 P1 与名单导出，保发布 / 审核 / 报名 |
| 外链失效 | 演示时链接打不开 | 准备本地备用链接，演示前逐个点开 |

### 14.4 已知限制

- 教务平台为模拟对接：登录使用演示账号，真实 SSO 需校方开放接口与授权。
- SQLite 在线上演示环境位于 `/tmp`，实例重启或重新部署会重置数据。
- 名单导出、签到、候补、推荐等属于 P1，不在本次范围。
- 外链报名活动的名额与结果以主办方系统为准，平台不做同步。

**建议优先落地（低成本、高观感）**：I2 时间冲突提醒、I10 群通知卡片、I7 复盘报告、I14 主办方认证徽章、I12 日历订阅。这五项都不依赖外部系统，能在现有 V5 框架上快速实现，也最适合现场演示。

**最具差异化（答辩亮点）**：I1 课表冲突检测 + I5 成长档案 + I3 候补自动补位，组合起来形成「报名前不冲突、参与后有积累、名额不浪费」的完整价值主张，是通用活动平台很少同时具备的能力。
